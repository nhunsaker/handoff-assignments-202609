# Assignment 05: how static-site frameworks turn page metadata into navigation

Budget **12 hours**. Slow, careful work; every claim verified by running a build, not by reading
about one.

## The question

When a page is added to a static site, where does it appear in the site's navigation — the
sidebar, the section list, the sitemap? Every framework answers this from page metadata
(frontmatter, filenames, config) plus a sort rule, and every framework's answer is slightly
different and incompletely documented. I want the actual rules, **verified empirically**, for
the frameworks people actually build with.

The output is a decision table: given a framework, a new page's metadata, and the existing
navigation, **predict the exact index where the new item lands** — and know when it will *not*
appear at all.

You may clone repositories and run builds. Nothing will be uploaded to you.

---

## Phase 0 — Environment (20 min)

Confirm Node (v20 or v22), `npm`, `pnpm`, `git`, and either Python 3 (for MkDocs) or the
ability to install it. Hugo needs its own binary — confirm you can fetch a release. Record what
you have in `environment.json`. Missing Hugo or Python is not a stop; skip that framework and

## Phase 1 — Document the rule (per framework, ~25 min)

From the **official documentation only**, record:

```json
{
  "framework": "eleventy",
  "version_tested": "3.0.0",
  "docs_url": "",
  "inclusion": {
    "what_makes_a_page_appear_in_nav": "verbatim from docs",
    "what_hides_it": "verbatim, e.g. draft: true, eleventyExcludeFromCollections"
  },
  "ordering": {
    "primary_key": "e.g. eleventyNavigation.order",
    "tie_break": "what the docs say happens when two pages share the same order value",
    "default_when_key_absent": "what the docs say happens when the key is missing",
    "direction": "ascending | descending | unspecified"
  },
  "grouping": {
    "how_sections_are_formed": "e.g. parent key, directory, _category_.json",
    "section_order_rule": ""
  },
  "docs_quotes": ["verbatim sentences supporting each field above"],
  "undocumented": ["every question above the docs do NOT answer"]
}
```

**`undocumented` is the field I care about most.** Tie-breaks and absent-key defaults are
where docs go quiet and where a predictor gets it wrong. If the docs do not say, write that
down — do not fill it from intuition. Phase 2 answers it.

## Phase 2 — Verify by building (per framework, ~45 min)

Clone the starter, build it once, and **save the navigation HTML** (the `<nav>`, sidebar, or
list that holds page links). Then run these probes, rebuilding and re-saving after each:

| probe | what you add | what you record |
|---|---|---|
| **P1 · plain** | one new page, minimal frontmatter, no ordering key | where it landed (index in the nav list), or "did not appear" |
| **P2 · explicit order** | same page with the ordering key set to land between two existing items | did it land exactly there |
| **P3 · tie** | order value **equal** to an existing item's | which came first, and by what evident rule (title? filename? date?) |
| **P4 · hidden** | the documented hide flag set | confirm it does not appear; confirm neighbours did not move |
| **P5 · nested** | a page inside an existing section/directory | which section it joined and its index within it |
| **P6 · delete** | remove an existing page | confirm the item vanished and everything below it moved up one |

For each probe:

```json
{
  "probe": "P3",
  "frontmatter_used": {"title": "Zz Test", "order": 3},
  "filename": "zz-test.md",
  "nav_selector": "the CSS selector that finds the nav list in the built HTML",
  "nav_items_before": ["Home", "About", "Blog"],
  "nav_items_after": ["Home", "About", "Zz Test", "Blog"],
  "landed_at_index": 2,
  "matched_documented_rule": true,
  "actual_rule_observed": "one sentence — what decided the placement",
  "build_output_path": "where the nav HTML lives in the build dir",
  "notes": ""
}
```

**Save the before/after nav HTML** for every probe to `output/<framework>/probes/P3-before.html`
and `P3-after.html`. Diffs I can read are worth more than your summary of them.

## Phase 3 — The decision table (60 min, after all frameworks)

`output/decision_table.json` — one entry per framework, executable as a rule where possible:

```json
{
  "framework": "eleventy",
  "will_appear_if": "eleventyNavigation.key is set AND not eleventyExcludeFromCollections",
  "index_rule": "sort siblings by eleventyNavigation.order ascending; missing order sorts LAST; ties broken by ... (from P3)",
  "section_rule": "eleventyNavigation.parent names the section by key",
  "sitemap_rule": "if the starter has a sitemap, how it orders — or 'no sitemap'",
  "confidence": "high | medium | low",
  "what_still_cannot_be_predicted": "anything Phase 2 could not pin down"
}
```

Plus `output/summary.json`: for each framework, how many of the six probes matched the
documented rule, how many revealed an undocumented rule, and how many could not be resolved.
**Undocumented-but-now-measured is the most valuable outcome** — that is the knowledge that
does not exist anywhere else.

---

## Phase 4 — Selectors (30 min)

For every framework, the **CSS selector that reliably locates the navigation list** in the
built HTML, and whether items are `<li>`, `<a>`, or nested `<details>`. Record whether the
nav's structure uses `nth-of-type`-stable markup or whether adding an item changes sibling
types (e.g. inserting a `<details>` between `<a>` elements). `output/selectors.json`.

## Rules

- **Every rule claim needs a build that demonstrates it.** A documented rule you could not
  reproduce in a probe is recorded as `matched_documented_rule: false` with what you saw
  instead. That is a finding, not a failure.
- **Verbatim doc quotes.** Copy the sentence; do not paraphrase what the docs "mean."
- **"The docs do not say" and "the probe could not resolve it" are both real answers.** Record
  them. Do not fill gaps from intuition about how a framework "probably" works.
- **Report environment failures as environment**, never as framework behaviour. A build that
  fails because Hugo is missing tells me nothing about Hugo.
- **Keep the starters pristine between probes** — revert your test page before the next probe
  so probes are independent.
- No analysis, recommendations, or commentary beyond the fields above. Return the files.
